Real programs are rarely written in a single file. Here’s a modular version using a helper function defined in a separate file.

**File: `main.c`**

```c
void print_hello();

int main() {
    print_hello();
    return 0;
}
```

**File: `hello.c`**

```c
#include <stdio.h>

void print_hello() {
    printf("Hello, world!\n");
}
```

Compile and link:

```bash
gcc -c main.c    # main.o
gcc -c hello.c   # hello.o
gcc main.o hello.o -o hello
./hello
```

This separation allows for more maintainable and testable code. If only `hello.c` changes, you can recompile it independently of `main.c`.

## Static Libraries: Internal and External Use

A **static library** is a collection of object files bundled into a `.a` archive. This allows internal code reuse without exposing every source file.

### Create a Static Library

```bash
ar rcs libhello.a hello.o
```

### Link It to the Main Program

```bash
gcc -c main.c
gcc main.o -L. -lhello -o hello
```

The flag `-lhello` tells the linker to look for `libhello.a`, and `-L.` tells it to look in the current directory.

### Linking an External Library

Suppose your program uses `sqrt()`, from the standard math library `libm.a`. You must link it explicitly:

```bash
gcc myprog.c -lm -o myprog
```

## Linking Order and Library Dependencies

The **order** in which object files and libraries are listed during linking **matters**.

### Why Order Matters

The linker processes files from left to right. It pulls symbols from a library only if something **already encountered** needs them.

Suppose:

* `main.o` calls `foo()`, defined in `libfoo.a`.
* `foo()` internally calls `bar()`, defined in `libbar.a`.

This works:

```bash
gcc main.o -lfoo -lbar -o prog
```

This may fail:

```bash
gcc main.o -lbar -lfoo -o prog
```

The linker sees `-lbar` first, finds nothing it needs, and moves on. Later, when it sees `foo()` in `-lfoo`, it needs `bar()`, but the linker doesn’t look back at `-lbar`.

### Circular Dependencies

If `libA` uses `libB`, and `libB` also uses `libA`, the linker cannot resolve all symbols in a single pass. You can address this by repeating libraries, but this is bad practice, you should always avoid circular dependencies.



## Optimization Flags

GCC provides several optimization levels that balance speed, size, and compilation time:

| Flag     | Description                                          |
| -------- | ---------------------------------------------------- |
| `-O0`    | No optimization (default when debugging).            |
| `-O1`    | Light optimizations.                                 |
| `-O2`    | Recommended default: good balance of speed and size. |
| `-O3`    | Aggressive inlining, unrolling, vectorization.       |
| `-Ofast` | Breaks IEEE compliance; trades precision for speed.  |
| `-Og`    | Optimizations safe for debugging.                    |

Example:

```bash
gcc -O2 -o prog prog.c
```

Use `time ./prog` or profiling tools to measure the performance impact.

## Architecture-Specific Flags: `-march` and `-mtune`

To squeeze extra performance from your machine, use:

* `-march=xxx`: Enable all instructions supported by a given architecture.
* `-mtune=xxx`: Optimize instruction scheduling and memory access patterns for a given CPU, but preserve compatibility.

```bash
gcc -O2 -march=native -mtune=native myprog.c -o myprog
```

`-march=native` auto-detects your current CPU and enables its instruction set. This is great for personal machines but may break portability on HPC clusters.

## A Demonstration of `-ffast-math` Pitfalls

The `-ffast-math` flag allows the compiler to reorder operations, ignore denormals, and apply algebraic simplifications. This can significantly **change numerical output**.

**File: `sum.c`**

```c
#include <stdio.h>
#include <stdlib.h>

void main()
{   
    int N = 2048;
    float a[N];
    float b = 0.0;

    for (int i = 0; i < N; i++) a[i] = 1.0f + i * i;
    for (int i = 0; i < N; i++) b += a[i];

    printf("%f\n", b);
}
```

Compile and run normally:

```bash
gcc sum.c -o sum
./sum    # Output: 2861220352.000000
```



Now with fast math:

```bash
gcc -O3 -ffast-math sum.c -o sum_fast
./sum_fast    # Output: 2861216000.000000
```

The difference in similar code can be due to loop reordering, vectorization, or fused multiply-add (FMA) instructions enabled by `-ffast-math`. Avoid this flag in scientific computing unless you're confident about the trade-offs.

## Header and Library Search Paths: `-I` and `-L`

* `-I<dir>`: Add an include path for `.h` files.
* `-L<dir>`: Add a library path for `.a` or `.so` files.

```bash
gcc -I./include -L./lib -lfoo main.c -o main
```

This tells the compiler to find headers in `./include` and libraries in `./lib`.

## Dynamic Linking and `LD_LIBRARY_PATH`

A **dynamic library** (or shared object) is loaded at **runtime**, not compiled into the binary. This keeps executables small and allows for library updates without recompilation.

To compile:

```bash
gcc main.c -L./lib -lsharedstuff -o prog
```

If `libsharedstuff.so` is not in a standard location, the program may fail to start. Use `LD_LIBRARY_PATH` to tell the system where to find shared libraries.

### In Bash:

```bash
export LD_LIBRARY_PATH=/path/to/your/libs:$LD_LIBRARY_PATH
```

Make this permanent by adding it to `~/.bashrc` or `~/.bash_profile`.

### In Other Shells:

* **zsh**: Add to `~/.zshrc` using `export` as above.
* **csh / tcsh**:

  ```csh
  setenv LD_LIBRARY_PATH /path/to/your/libs:$LD_LIBRARY_PATH
  ```
* **fish**:

  ```fish
  set -x LD_LIBRARY_PATH /path/to/your/libs $LD_LIBRARY_PATH
  ```

Use `ldd ./prog` to inspect which shared libraries your program depends on.
