# Programs, Processes, and System Resources

Suppose you want to run the same simulation at four temperatures.
Before starting all four runs, you need to consider CPU cores, memory, and
output files. These are the resources that determine how many calculations
you can run effectively on a machine.

## One program, several runs

A **program** is the code you execute. A **process** is one running instance
of that program, with its own working data and execution state.

If your simulation is a serial program, starting it once for each temperature
creates four processes. Each has a **PID** (process identifier), which lets
you identify that particular run when checking or stopping it.

The program may be the same, but the input parameters, progress, and results
of the four runs are different.

## CPU cores: how many calculations at once?

A single-threaded simulation can use at most one CPU core at a time. Running
it on a machine with 32 cores does not automatically make it 32 times faster.

Four independent, single-threaded runs can use four cores simultaneously,
provided those cores are available. If only two cores are available, the
operating system shares CPU time between the runs. Starting more processes
then does not provide more computing power.

Two useful measures of run time are:

- **Wall time**: the elapsed time from start to finish — how long you wait.
- **CPU time**: the time spent executing on CPUs. Waiting for disk input or
  for an available core contributes to wall time without contributing CPU time
  to that process.

A calculation can therefore be alive but use little CPU while waiting for data.
For parallel work, CPU time summed over its workers can exceed wall time.

## RAM: does each run fit?

Each independent run normally needs its own arrays and other working data.
For example, an array of $10^8$ values stored as 8-byte floating-point numbers
occupies about **800 MB** (decimal units).

If each run holds three such arrays, four simultaneous runs need about
**9.6 GB just for those arrays**. The program, temporary arrays, libraries,
and operating system require additional memory.

Exceeding available RAM can cause severe slowdowns if data is moved to swap,
failed allocations, or termination of a process. Estimate memory requirements
before deciding how many runs to start together.

## Independent runs or a parallel simulation?

These are different ways to use several cores:

| Approach | Typical use |
| --- | --- |
| Independent processes | Different temperatures, initial conditions, or random seeds |
| Several cooperating processes | One calculation split with MPI |
| Several threads within a process | Shared-memory parallelism, for example with OpenMP |

Threads share a process's memory; separate processes normally have separate
address spaces. MPI programs must arrange data exchange, while threaded code
must coordinate access to shared data. Both require suitable code or libraries.

Check how many threads each run actually uses. Four runs that each start eight
threads create 32 threads competing for resources, not four. Numerical libraries
can start threads even when your own code contains no explicit parallelism.

## Output files: keep runs separate

Separate process memory does not imply separate files. If all four runs write
to the same `results.dat`, they can overwrite or mix results.

Use a separate output directory for each run, for example:

```text
runs/
├── T_1.0/
├── T_1.5/
├── T_2.0/
└── T_2.5/
```

Keep each run's input parameters and results together. For stochastic
simulations, record the random seed as well.

## Before launching a batch

Check three things: **cores per run, memory per run, and a distinct output
location for each run**. On a shared cluster, use the resources allocated to
your job, rather than assuming the entire machine is available.
