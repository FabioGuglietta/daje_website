# Fused Multiply-Add (FMA) and the Roofline Model


## What is an FMA?

An **FMA** computes:

[
\text{FMA}(a,b,c) = a \cdot b + c
]

in **one instruction**, typically with **one rounding at the end** (as opposed to rounding after the multiply and again after the add).

### Why it matters

* **Performance:** on many CPUs, FMA has similar throughput to a multiply, so you get “multiply+add” work at almost the cost of one operation.
* **Accuracy:** one rounding can slightly change results vs doing `a*b + c` as two separate operations (two roundings).

> [!NOTE]
> The accuracy difference is often a good thing (less rounding), but it means **results may not match bit-for-bit** when you compare FMA vs non-FMA evaluation.


## ISA and naming (what to expect)

### x86-64

* FMA is typically **FMA3** (three-operand form), instructions like `vfmadd132pd`, `vfmadd231ps`, etc.
* Available with AVX + FMA (common on Intel/AMD server CPUs for years).

### ARM NEON (Advanced SIMD)

* FMA-style ops exist, e.g. `fmla` in AArch64 NEON.

### ARM SVE

* Predicated fused multiply-add exists as SVE instructions and intrinsics.

In C/C++ you usually see FMA in one of three ways:

1. compiler recognizes a pattern and emits FMA
2. you call `fma()` (math library function, slower unless inlined/recognized)
3. you use intrinsics (explicit control)


## When will the compiler generate FMA?

### Pattern recognition

Compilers may fuse `a*b + c` into an FMA if allowed.

### The key restriction: floating-point semantics

With strict IEEE semantics, `a*b + c` as two operations is not necessarily identical to fused (one rounding). Therefore:

* Some compilers will only fuse under “fast math” modes.
* Some will fuse when the target ISA guarantees correct fused semantics and the compiler is configured to allow contraction.

Important knobs:

* GCC/Clang: `-ffp-contract=fast` (enable contraction)
* “fast math” bundles (more aggressive, potentially unsafe for numerics): `-ffast-math`

> [!IMPORTANT]
> Do not assume FMA will appear just because the CPU supports it. Always check assembly or use compiler reports.


## Benchmark plan: build a roofline from two measurements

A roofline model needs:

1. **Peak compute throughput** (GFLOP/s), ideally from a compute-heavy kernel (high arithmetic intensity)
2. **Peak sustainable memory bandwidth** (GB/s), from a streaming kernel
3. For each kernel: **Arithmetic Intensity** (FLOP/byte) and measured performance (GFLOP/s)

Then one computes

[
P_{\max}(I) = \min(P_{\text{peak}},; B_{\text{mem}} \cdot I)
]

where:

* (P_{\text{peak}}) is peak GFLOP/s
* (B_{\text{mem}}) is memory bandwidth in GB/s
* (I) is arithmetic intensity (FLOP/byte)


# Part A — Code: benchmark kernels (C)

We will benchmark two kernels:

1. **STREAM-like triad** (memory-bound):
   [
   a[i] = b[i] + s \cdot c[i]
   ]
   This is a classic “roofline bandwidth” kernel.

2. **Compute-heavy FMA chain** (compute-bound):
   repeatedly do FMAs on values kept in registers (very high arithmetic intensity).

## 1) `bench_fma.c`

```c
// bench_fma.c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <time.h>
#include <math.h>

#ifndef RESTRICT
#define RESTRICT __restrict__
#endif

static inline double now_sec(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return (double)ts.tv_sec + 1e-9 * (double)ts.tv_nsec;
}

static void *aligned_malloc(size_t alignment, size_t size) {
    void *ptr = NULL;
    if (posix_memalign(&ptr, alignment, size) != 0) return NULL;
    return ptr;
}

// Prevent the compiler from optimizing away results
static volatile double sink_d = 0.0;

// ------------------------------------------------------------
// Kernel 1: STREAM-like triad: a[i] = b[i] + s*c[i]
// FLOPs per element: 2 (mul + add); if FMA is used, still counts as 2 FLOPs.
// Bytes per element (naive): load b (8) + load c (8) + store a (8) = 24 bytes.
// (Write-allocate may add extra traffic; we use this as a simple model.)
// ------------------------------------------------------------
double triad(int n, double * RESTRICT a, const double * RESTRICT b,
             const double * RESTRICT c, double s) {
    double t0 = now_sec();
    for (int i = 0; i < n; i++) {
        a[i] = b[i] + s * c[i];
    }
    double t1 = now_sec();
    // consume one value to keep it "used"
    sink_d += a[n/2];
    return t1 - t0;
}

// ------------------------------------------------------------
// Kernel 2: compute-heavy FMA chain
// Keep values in registers and do many FMAs per iteration.
// This inflates arithmetic intensity to become compute-bound.
// ------------------------------------------------------------
double fma_chain(int iters) {
    // Start with some values that aren't compile-time constants
    double x = 1.0000001, y = 1.0000002, z = 0.9999999, w = 1.0000003;
    double t0 = now_sec();

    // Each loop body has many multiply-add patterns.
    // Compilers can fuse these into FMA depending on flags.
    for (int i = 0; i < iters; i++) {
        x = x * y + z;
        y = y * z + w;
        z = z * w + x;
        w = w * x + y;

        x = x * y + z;
        y = y * z + w;
        z = z * w + x;
        w = w * x + y;

        x = x * y + z;
        y = y * z + w;
        z = z * w + x;
        w = w * x + y;

        x = x * y + z;
        y = y * z + w;
        z = z * w + x;
        w = w * x + y;
    }

    double t1 = now_sec();
    sink_d += x + y + z + w;
    return t1 - t0;
}

int main(int argc, char **argv) {
    int n = (argc > 1) ? atoi(argv[1]) : (1<<24);      // ~16 million doubles -> 128 MiB arrays
    int iters = (argc > 2) ? atoi(argv[2]) : (1<<26);  // tune to get stable runtimes

    printf("n=%d doubles per array\n", n);
    printf("iters=%d for fma_chain\n", iters);

    // Allocate arrays (64B alignment is fine)
    double *a = (double*)aligned_malloc(64, (size_t)n * sizeof(double));
    double *b = (double*)aligned_malloc(64, (size_t)n * sizeof(double));
    double *c = (double*)aligned_malloc(64, (size_t)n * sizeof(double));
    if (!a || !b || !c) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }

    for (int i = 0; i < n; i++) {
        b[i] = 0.5 + 1e-9 * (double)i;
        c[i] = 1.5 + 1e-9 * (double)(n - i);
        a[i] = 0.0;
    }

    // Warm-up
    triad(n, a, b, c, 1.234);
    fma_chain(iters/8);

    // Measure triad
    double t_triad = triad(n, a, b, c, 1.234);
    // Model: 2 flops per element
    double flops_triad = 2.0 * (double)n;
    // Model: 24 bytes per element
    double bytes_triad = 24.0 * (double)n;

    double gflops_triad = flops_triad / t_triad / 1e9;
    double gbs_triad = bytes_triad / t_triad / 1e9;

    printf("\nTRIAD:\n");
    printf("  time = %.6f s\n", t_triad);
    printf("  perf = %.3f GFLOP/s (model)\n", gflops_triad);
    printf("  BW   = %.3f GB/s   (model)\n", gbs_triad);
    printf("  AI   = %.6f flop/byte (model)\n", flops_triad / bytes_triad);

    // Measure compute-heavy FMA chain
    double t_fma = fma_chain(iters);
    // Loop body: 16 expressions of the form x=x*y+z (per iteration)
    // Each contributes 2 FLOPs (mul+add). Total FLOPs = 16 * 2 * iters = 32*iters
    double flops_fma = 32.0 * (double)iters;
    double gflops_fma = flops_fma / t_fma / 1e9;

    printf("\nFMA_CHAIN:\n");
    printf("  time = %.6f s\n", t_fma);
    printf("  perf = %.3f GFLOP/s (model)\n", gflops_fma);
    printf("  (AI is very high; intended to be compute-bound)\n");

    // Print sink to avoid dead-code elimination across compilation units
    printf("\nsink = %.6e\n", sink_d);

    free(a); free(b); free(c);
    return 0;
}
```


# Part B — Run it with and without FMA contraction

## Compile commands (x86 example)

### Strict-ish (often less FMA contraction)

```bash
gcc -O3 -march=native bench_fma.c -o bench_strict
```

### Allow contraction (encourage FMA)

```bash
gcc -O3 -march=native -ffp-contract=fast bench_fma.c -o bench_fma
```

### Aggressive (also allows reordering, not always acceptable)

```bash
gcc -O3 -march=native -ffast-math bench_fma.c -o bench_fast
```

Inspect assembly for FMA on x86:

```bash
objdump -d -Mintel bench_fma | grep -i fmadd | head
```

On ARM (NEON/SVE machines), you’d look for `fmla` / SVE equivalents.


# Part C — Build the roofline plot (Python)

This script:

* runs your executable a few times,
* extracts measured **BW** and **GFLOP/s**,
* computes a simple roofline,
* plots measured points vs roofline.

Save as `roofline_plot.py`:

```python
import re
import subprocess
import numpy as np
import matplotlib.pyplot as plt

def run(exe, n=None, iters=None):
    cmd = [exe]
    if n is not None: cmd.append(str(n))
    if iters is not None: cmd.append(str(iters))
    out = subprocess.check_output(cmd, text=True)
    # Extract numbers
    bw = float(re.search(r"BW\s+=\s+([0-9.]+)\s+GB/s", out).group(1))
    gflops_triad = float(re.search(r"TRIAD:.*?perf\s+=\s+([0-9.]+)\s+GFLOP/s", out, re.S).group(1))
    gflops_fma = float(re.search(r"FMA_CHAIN:.*?perf\s+=\s+([0-9.]+)\s+GFLOP/s", out, re.S).group(1))
    return bw, gflops_triad, gflops_fma, out

def main():
    exe = "./bench_fma"   # change as needed
    # Tune sizes if needed
    n = 1<<24
    iters = 1<<26

    # Run multiple trials and take best (typical for roofline-style measurement)
    trials = 5
    bws, triads, fmas = [], [], []
    last_out = None
    for _ in range(trials):
        bw, gt, gf, out = run(exe, n, iters)
        bws.append(bw); triads.append(gt); fmas.append(gf)
        last_out = out

    bw_peak = max(bws)
    triad_perf = max(triads)
    fma_perf = max(fmas)

    # Arithmetic intensity (model)
    ai_triad = 2.0 / 24.0  # flop/byte for triad model
    # For fma_chain, AI is huge; treat as compute-bound and plot at high AI
    ai_fma = 50.0

    # Peak compute from measured compute-heavy kernel
    p_peak = fma_perf

    # Roofline curve
    I = np.logspace(-3, 3, 400)  # flop/byte
    roof = np.minimum(p_peak, bw_peak * I)

    print("=== Measurements (best of trials) ===")
    print(f"Peak BW (from triad model): {bw_peak:.2f} GB/s")
    print(f"Triad perf:                {triad_perf:.2f} GFLOP/s at AI={ai_triad:.4f}")
    print(f"Compute peak (from chain): {p_peak:.2f} GFLOP/s (proxy for peak compute)")
    print("\nLast run output:\n", last_out)

    plt.figure()
    plt.loglog(I, roof)
    plt.scatter([ai_triad, ai_fma], [triad_perf, fma_perf], marker='o')
    plt.xlabel("Arithmetic intensity (FLOP/byte)")
    plt.ylabel("Performance (GFLOP/s)")
    plt.title("Roofline model (measured BW + measured compute proxy)")
    plt.grid(True, which="both")
    plt.show()

if __name__ == "__main__":
    main()
```

Run:

```bash
python3 roofline_plot.py
```

> [!NOTE]
> This is a *teaching roofline*: we use a STREAM-like triad as a bandwidth proxy and a compute-heavy chain as a compute proxy. For serious rooflines you’d separate L1/L2/L3/DRAM roofs and use more careful traffic models (e.g., write-allocate, non-temporal stores).


## What you should see

* The **TRIAD** point should land near the **slanted bandwidth roof** because its arithmetic intensity is low (~0.083 flop/byte in our simple model).
* The **FMA_CHAIN** point should sit near the **flat compute roof** because it keeps values in registers and has extremely high arithmetic intensity.

If FMA contraction is enabled and your CPU supports FMA well:

* `FMA_CHAIN` GFLOP/s may increase noticeably when compiled with `-ffp-contract=fast` or `-ffast-math`.
* TRIAD typically won’t change much (it’s bandwidth-limited; FMA doesn’t fix memory).


## Optional: a more explicit “FMA vs non-FMA” comparison

To force a difference, you can compile the same code twice:

* one with contraction allowed (`-ffp-contract=fast`)
* one with contraction disabled (`-ffp-contract=off`)

For GCC/Clang:

```bash
gcc -O3 -march=native -ffp-contract=off  bench_fma.c -o bench_no_fma
gcc -O3 -march=native -ffp-contract=fast bench_fma.c -o bench_fma
```

Then compare `FMA_CHAIN` performance and check assembly (`fmadd` vs separate `mul`+`add`).


## Where this fits in the larger optimization story

* FMA is mainly a **compute-throughput** tool.
* Whether it matters depends on whether your kernel is **compute-bound** or **memory-bound**.
* The roofline model tells you which regime you are in:

  * **below the slanted line** → bandwidth-limited → focus on memory traffic, layout, reuse
  * **near the flat line** → compute-limited → focus on vectorization, FMA, instruction throughput, unrolling
