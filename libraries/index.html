Libraries

In any real-world programming project, it’s rarely a good idea to put everything into a single source file. As programs grow larger and more complex, it becomes crucial to organize code into modules — pieces of code that can be developed, tested, and reused independently. This is where libraries come in.

A library is simply a collection of functions and data structures that have been precompiled and packaged together, so they can be reused across multiple programs. Libraries promote:

  • Code reuse: write once, use everywhere

  • Separation of concerns: isolate utilities, algorithms, and I/O

  • Faster compilation: you compile your core code once, not every time

  • Cleaner codebases: your main.c doesn’t have to become a monster

Note

What is a Library?¶

A library is simply a collection of object code (compiled .o files) that are bundled into a single file. There are two main types:

  • Static libraries (.a files): linked at compile time.

  • Shared libraries (.so files): linked at runtime. These can be created from any language that compiles to object code, including C, C++, and Fortran.

Static Libraries (.a)¶

A static library is a collection of object files that are linked into your executable at compile/link time. Once the linking happens, the code from the library becomes part of the final binary.

Characteristics¶

  • File extension: .a (on Unix/Linux), .lib (on Windows)

  • Code is copied into the executable

  • No need for external files at runtime

  • Larger binary size, but self-contained

When to Use¶

  • When you want to distribute a single executable (e.g., for embedded systems)

  • When the library doesn’t change often

  • When runtime dependencies are not desirable

Example: Creating a Static Library¶

Suppose you have a math module:

math_utils.c¶

int add(int a, int b) {
    return a + b;
}

int square(int x) {
    return x * x;
}

math_utils.h¶

#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int add(int a, int b);
int square(int x);

#endif

Compile into object file:

gcc -c math_utils.c

Create the static library:

ar rcs libmath.a math_utils.o
Note

The command:

ar rcs libmath.a math_utils.o

is used to create a static library in Unix-like systems using the ar (archive) tool. Let’s break it down:

  • ar The archiver program — used to create, modify, and extract from archive files (like .a libraries)

  • r Replace or add the named files (math_utils.o) into the archive (libmath.a)

  • c Create the archive if it doesn’t already exist (suppress warning if it does)

  • s Write an index (also called a symbol table) to speed up linking later — essential for linking with gcc

  • libmath.a The name of the static library you’re creating. Conventionally, static libraries start with lib and end with .a

  • math_utils.o The object file to be added into the archive (i.e., your compiled code)

Use it in a program:

// main.c
#include <stdio.h>
#include "math_utils.h"

int main() {
    printf("add(2, 3) = %d\n", add(2, 3));
    return 0;
}

Compile and link with the static library:

gcc main.c -L. -lmath -o myprog
Note

-lmath corresponds to libmath.a (just strip off the lib prefix and .a suffix)

Warning

Make sure the library is in the current directory (or add -L/path/to/lib).

Shared (or Dynamic) Libraries (.so)¶

A shared library is compiled code that remains separate from your executable. The program loads and links to it at runtime.

Characteristics¶

  • File extension: .so (shared object, Unix/Linux), .dll (Windows)

  • Not embedded into the executable

  • Smaller executables

  • Must be available when the program runs

When to Use¶

  • When the library is used by many programs

  • When you want to update the library without recompiling everything

  • When you care about memory efficiency

Example: Creating a Shared Library¶

Compile the shared library:

gcc -fPIC -c math_utils.c
gcc -shared -o libmath.so math_utils.o
Note

  • -fPIC: “Position Independent Code” — this tells the compiler to generate machine code that can be loaded at any memory address. This is mandatory for shared libraries because the same code may be loaded by different programs in different memory locations.

  • -shared: tells the compiler/linker to produce a shared object (.so) file, i.e., a shared library.

  • -o libmath.so: specifies the output file — here, libmath.so (by convention, shared libraries use the .so extension).

  • math_utils.o: the object file to include in the shared library.

Compile the program:

gcc main.c -L. -lmath -o myprog

Run it:

LD_LIBRARY_PATH=. ./myprog
Note

LD_LIBRARY_PATH is an environment variable that tells the dynamic linker (ld.so) where to look for shared libraries at runtime. By default, the linker only searches in standard system paths. If your shared library (e.g., libmath.so) is in the current directory, it won’t find it unless you tell it explicitly. Therefore, to execute, you must run LD_LIBRARY_PATH=. ./myprog. If you don’t do this, you’ll get an error like: error while loading shared libraries: libmath.so: cannot open shared object file: No such file or directory

Fortran Support¶

Fortran supports both static and shared libraries using exactly the same process:

Static (libmymod.a)¶

gfortran -c module1.f90
ar rcs libmymod.a module1.o

Shared (libmymod.so)¶

gfortran -fPIC -c module1.f90
gfortran -shared -o libmymod.so module1.o

And use them as you would in C.
